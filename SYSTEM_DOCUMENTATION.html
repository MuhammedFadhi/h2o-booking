SA'DA H2O — Installation Booking & Warranty System

A browser-only web app that runs the full lifecycle of a SA'DA H2O reverse-osmosis water-purifier sale in Saudi Arabia's Eastern Province: a customer books an installation → an installer completes the job and scans each unit's QR → each unit becomes a warranty → the warranty drives filter and service reminders. One admin dashboard runs all of it.

No build step — static HTML + CDN scripts Hosted on Vercel Data on Supabase (Postgres, Bahrain region) SMS via Taqnyat relay 44 migrations shipped
01 — How the pieces fit

Architecture

Three static front ends talk directly to Supabase with a public anon key; a thin layer of Vercel serverless functions holds the two things a browser must never hold — the Supabase service-role key and the SMS relay's shared secret.

Solid arrows = data reads/writes at runtime. Dashed arrow = the service-role path used only by /api/admin/* endpoints, migrated one panel at a time from the dashboard's direct client.

05 — Rules that shape the code

Key flows & invariants

The behaviors most likely to surprise someone extending this system.

1

Booking is one atomic transaction

A slot used to be reserved (UPDATE) then a booking inserted (INSERT) as two client calls — a dropped connection mid-flow could strand a slot as booked with no booking behind it. The create_booking RPC (v31) locks the slot, checks it's free and in-region, reserves it, and inserts — all or nothing.

Never revert to two-step reserve-then-insert
2

Orphaned slots self-heal

An abandoned admin reschedule can still leak a slot. The Overview panel shows a banner with a one-click "Free them" whenever a slot is marked booked with no active booking behind it.

3

One booking, many warranties

A booking can install several units. warranties.booking_id is the authoritative many-side; bookings.warranty_id only holds one representative pointer. To see every unit from a booking, query warranties by booking_id — there is deliberately no one-warranty-per-booking constraint.

4

Warranty activation is a two-scan handshake

Since v39, the installer's photo creates a pending warranty per RO unit; the customer's own QR scan attaches the serial and activates it. Since v41, the 90-day filter and 365-day service countdowns start on that customer scan, not on install completion.

5

Dispensers carry no QR and no warranty

Detected by is_serialized = false on the product row. The installer's scan checklist skips them entirely; they generate no reminders.

6

Reminders are manual, not cron

Filter (90-day) and service (365-day) due dates live on each warranty. A 🔔 admin action sends due reminders through the existing SMS relay — by design there is no scheduled job. Opted-out and non-serialized units are excluded.

06 — How the schema got here

Migration history

44 hand-run, idempotent SQL files in migrations/, applied top-to-bottom in the Supabase SQL editor — never auto-applied. A schema change and its code are shipped as a pair; skipping one is the most common cause of a post-deploy break.

v22Security overhaul + polish

48-hour lead time trigger, admin_emails + is_admin(), dark-first admin/installer theme, toast/modal system, real-time dashboard, in-browser QR scanner (jsQR), PWA for installers.

v23Installer self-serve claim

is_installer() function; installers can browse and atomically claim unassigned bookings.

v24Round-robin auto-assignmentsuperseded by v25

Auto-picks the active installer with the fewest ongoing jobs. Retained in the repo for history only — do not run on a fresh database.

v25Service regions

Introduces grouped-city service_regions as the slot/booking scope; reverts to self-serve claim over auto-assign.

v26RLS lockdown + phone normalization

Closes an audit finding: anon could freely SELECT/UPDATE/DELETE bookings, disable OTP, and read installer PII. Locked to admin-only where it matters.

v27Warranty CRM merged in

Ports the standalone PHP/MySQL warranty CRM into this app: warranties, product_models, warranty_service_history, customer_followups. Phone+bcrypt auth replaced by phone+OTP.

v28Warranty status + admin activation

Adds active / paused / deactivated status; admin can activate a warranty straight from a completed install.

v30Admin activity log

Lightweight audit trail — who did what, when — for cancels, completions, reschedules, warranty state changes, bulk ops.

v31Atomic booking creation

Fixes the slot-reservation leak: the create_booking RPC replaces the two-step client-side reserve-then-insert. See Key flows above.

v32Booking ↔ warranty ↔ service links

Wires bookings.warranty_id, adds service opt-out and manual "mark as serviced".

v33Backfill customer names

Copies a name from a booking onto a nameless customers row (QR-registered customers who never typed one).

v34Product catalogue + prices

Adopts the 5-product official catalogue with SAR prices; customers pick product + quantity at booking time.

v35Multi-product baskets

Adds booking_items so one booking can hold several product lines with independent serialization.

v36Real product images

Replaces the generic placeholder image used across the whole catalogue with real per-product photos.

v37Jeddah region · promo codes · invoices

Three features at once: a new service region, discount promo_codes, and the invoices payment lifecycle table.

v38Referral source

Optional "where did you hear about us?" captured at booking time for channel attribution.

v39Customer-driven activation + admin booking

Warranty gains a pending status: the installer's photo creates it, the customer's own QR scan attaches the serial and activates it.

v40Fix customer-scan expiries

Bugfix: the SECURITY DEFINER activation function ran as its owner, not anon, so an expiry-date guard trigger never fired for customer-driven scans.

v41Countdown starts on scan

Filter (+90d) and service (+365d) expiries now start at the customer's QR scan, not at install completion.

v42Clearer activation errors

Separates "booking exists but isn't installed yet" from "no booking at all" — previously both returned the same opaque no_booking reason.

v43RLS hardening, phase 1

Audit found anon could read invoices (financial data) despite no public page needing it. Locked out.

v44Commercial products + city cleanup

Adds 200/400 GPD commercial RO systems to the catalogue; expands and de-duplicates the city list.

09 — Read before you touch these

Known constraints & deliberate risks

!

Customer auth is client-side OTP in localStorage

Anyone who knows a customer's phone number could in principle access that customer's portal session. This is a known, deliberately-deferred decision, not an active bug — revisit if customer-account privacy becomes a hard requirement.

!

A migration and its code are a pair

Migrations are never auto-applied. Shipping code without its matching migration (or vice versa) is the most common cause of a post-deploy error — check the migration first if something breaks right after a push.

!

Anon can insert and update, but never delete bookings

Needed for public booking and installer auto-activation to work without a login — but it also means a test booking made from a public session can't be removed from that session; delete it from the admin dashboard instead.

!

The SMS relay path is off-limits to casual edits

api/send-sms.js and the DigitalOcean droplet are wired to Taqnyat with a fixed static IP required by Saudi telecom law. Changing them risks breaking all outbound SMS. Never commit the Taqnyat bearer token to this repo.

✓

Two product vocabularies coexist deliberately

Old warranties reference legacy model names (A100, A1UV…); new sales use the 5-product catalogue introduced in v34. Both are valid at once — this is intentional, not debt to clean up.

✓

STC blocks Netlify in Saudi Arabia

Netlify support was removed entirely in v26 for this reason. Vercel is the only supported host — do not reintroduce a Netlify deployment path as a fallback.
